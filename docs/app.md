# 화면 (app)

> 담당 브랜치: `app_branch` · 담당 파일: `src/app/`, `tests/test_app.py`
> 이 문서는 해당 영역의 PR에서만 수정한다 ([협업 방식](workflow.md)).

Streamlit 챗봇 화면이다. 질문을 입력하면 파이프라인(`src/rag`의 `answer()`)을 실행해 **답변, 근거 판정 배지, 인용한 논문, 검색된 논문 전체**를 보여준다. 파이프라인은 호출만 하고 고치지 않는다.

```bash
uv run streamlit run src/app/main.py
```

## 구성

| 파일 | 역할 |
| --- | --- |
| `src/app/main.py` | 진입 스크립트: 설정 사이드바, 대화 기록, 입력 처리 |
| `src/app/view.py` | 답변 하나를 그리는 부품(배지, 답변, 경고, 출처, 검색된 논문) |
| `src/app/logic.py` | streamlit을 쓰지 않는 순수 함수: 파이프라인 호출, 상태 배지, 경고, 번호 붙은 논문 가공 (pytest로 직접 검증) |

판단(어떤 배지·경고를 보일지)은 `logic.py`에, 그리는 일은 `view.py`에 둬서 판단을 화면 없이 테스트한다.

## 보이는 것

- **상태 배지**: 근거 충분(초록) / 일부만 근거 있음(주황) / 근거를 찾지 못함(빨강) / 점수 게이트 통과(`score` 게이트일 때). 모델이 스스로 거절한 경우도 "근거를 찾지 못함"으로 보인다.
- **출처**: 답변이 실제로 인용한 논문만, 답변 속 `[n]`과 같은 번호로 보여준다(번호 = 검색 순위).
- **검색된 논문 전체**(접힘): 유사도 점수, 초록 일부, 답변이 인용했는지 표시. 거절된 질문에서도 "무엇이 검색됐는데 왜 근거가 못 됐는지" 볼 수 있다.
- **경고**: 존재하지 않는 논문 번호를 인용했거나 인용이 하나도 없으면 답변 아래에 표시한다. 정제에서 `math_loss`가 붙은 논문에는 "수치 일부 누락"이 붙는다.
- 사이드바: 검색 방식(`max`/`original`), 근거 판단(`judge`/`score`)을 바꿔 가며 같은 질문을 비교할 수 있다. 기본은 측정으로 정한 `max` + `judge`. 답변 모델과 검색 대상 논문 수도 보여준다.
- 예시 질문 4개: 되는 질문 3개와 거절되는 질문 1개. 평가 질문과 겹치지 않게 새로 쓰고 실제로 돌려 보고 골랐다.

## 설계 결정

- **질문마다 독립적으로 처리한다(이전 대화를 기억하지 않는다).** 후속 질문("그럼 온도는?")을 지원하려면 질문 재작성이 필요한데, 이 프로젝트의 평가는 모두 단일 질문 기준이라 측정하지 않은 기능을 얹지 않았다. 화면 상단에 그 사실을 적었다.
- **스트리밍은 쓰지 않는다.** 판정과 인용 검증이 답변 전체가 있어야 가능해서 `answer()`가 한 번에 결과를 돌려준다. 대신 스피너로 진행 중임을 알린다. 질문당 LLM 호출이 여러 번(재작성, 판정, 답변)이라 느리다.
- **오류는 종류만 보여주고 메시지는 숨긴다.** 무료 API 한도·네트워크 오류가 나도 앱이 죽지 않고 안내만 보이며, 오류 메시지에 키 같은 값이 섞일 위험을 피한다. (테스트로 고정)
- 논문 제목·초록·LLM 답변에 `$`가 있으면 마크다운이 수식으로 읽어 글이 깨져서 `$`를 이스케이프한다.
- `streamlit run`은 스크립트 폴더만 import 경로에 넣어서 `main.py`가 프로젝트 루트를 직접 추가한다.

## 실제로 띄워 보고 찾은 문제

단위 테스트만으로는 놓친 것들이다. 브라우저에서 직접 눌러 보고 찾아 고쳤고, 1·2번은 회귀 테스트를 추가했다.

1. **"대화 지우기" 버튼이 첫 답변 뒤에도 비활성**이었다. 사이드바는 질문을 처리하기 전에 그려지는데, 버튼의 활성 여부를 "대화가 있는지"로 정해 한 박자 늦었다. (AppTest가 잡았다) 항상 활성으로 바꿨다.
2. **대화를 지우면 방금 고른 예시 질문이 다시 자동 실행**됐다. 예시 버튼의 선택 상태가 남아 있다가 다시 나타나면서 선택된 채로 질문이 들어갔다. 지울 때마다 예시 버튼의 `key`를 바꿔 새 위젯으로 만들었다. 옛 동작을 흉내 낸 복사본에서 이 테스트가 실제로 질문이 두 번 실행되는 것을 잡는지도 확인한다.
3. **"범위 밖" 예시가 사실은 범위 안이었다.** 처음 넣은 리튬이온 양극 소재 질문은 코퍼스에 XRD 결정립 크기 분석 논문(리튬 스피넬 소재)이 있어, 판정이 근거 충분으로 보고 그 논문에 근거해 답했다(정상 동작). 거절 예시로는 틀린 선택이라 실제로 여러 질문을 돌려 보고 바꿨다. 지금 예시(웨이퍼 불량 분류에 필요한 GPU 사양)는 검색 점수가 0.52로 점수 게이트(0.30)는 통과하지만 판정이 "논문에 GPU 사양은 없다"며 거절한다. 점수만으로는 못 거르는 질문을 판정이 거르는 사례 하나다(일화이며 통계가 아니다).
4. 거절 답변이 본문과 "근거 판정 이유"에 같은 문장을 두 번 보여줘서 중복을 숨겼다.

## 한계

- 한 사용자의 로컬 실행만 가정했다. 배포(인증, 동시 접속, API 한도 공유)는 다루지 않았다.
- 매 질문마다 FAISS 인덱스와 메타데이터 파일을 다시 읽는다(논문 314편 규모라 문제는 없었지만 규모가 커지면 캐시가 필요하다).
- 화면 자체의 사용성은 사용자 평가 없이 만든 사람이 눈으로 확인한 수준이다. 모바일 화면은 확인하지 않았다.
- 화면은 파이프라인의 한계를 그대로 가진다: 초록만 근거라 수치·실험 조건은 약하고, 코퍼스에 없는 주제는 답하지 못한다([평가 문서](evaluation.md)).
